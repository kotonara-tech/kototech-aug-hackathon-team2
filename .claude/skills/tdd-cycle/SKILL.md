# /tdd-cycle

Red → Green → Refactor を 1 周、専任サブエージェントへの委譲で回す。**Red は失敗の実出力（期待値 vs 実測値）を
目視確認するまで Green に進まない。これが最重要ルール。**

## 使い方

### Red
1. `test-designer` に機能要求を渡し、Given-When-Then のシナリオと `(domain|api|web, @agent)` タグ付き ToDo を作らせる
2. ToDo ごとに対応する `@domain-implementer` / `@api-implementer` / `@web-implementer` に **テストだけ** を書かせる
   （このフェーズでは `src/` を触らない。禁止事項として明示的に渡す）
3. `npx vitest run tests/<file>.test.ts` を実行し、**期待どおりの理由で失敗しているか**を実出力で確認する
   （import エラーなど別の理由で落ちていないか要注意）

### Green
4. 同じ実装エージェントに本体実装をさせる（このフェーズでは `tests/` を触らない。禁止事項として明示的に渡す）
5. 最小実装でテストを通す。完璧さは求めない
6. 詰まった場合（原因不明の Red が続く）は `failure-analyst` に切り分けを依頼する

### Refactor
7. 同じ実装エージェントがテストを通したままコードを整理する
8. `npx vitest run tests/<file>.test.ts` を再実行し Green を維持していることを確認する

### 仕上げ
9. `code-reviewer` / `test-reviewer` / `security-reviewer` に監査させる（並行実行可）

## TDD 適用外の扱い

以下は Red を省略してよい。**ただし省略した理由を必ず明示する。**

- 設定ファイル・依存追加・スキャフォールドなど振る舞いを持たない変更
- 調査・実験用の使い捨てコード（本体に取り込む時点で TDD に戻す）
- 既存コードの読解、ドキュメントのみの編集

## 出力

各フェーズの担当エージェント名、実行した vitest コマンドと実出力、適用外と判断した場合はその理由。

## 禁止

- Red を飛ばして Green から始めること
- テストを書き換えて通すこと（期待値を実装に合わせて緩める）
- 失敗の実出力を確認せずに「テストを書いた」で次に進むこと
- 結果を偽ること（実際は落ちているのに通ったと報告する）
